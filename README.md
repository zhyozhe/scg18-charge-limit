# Galaxy A23 (SCG18) の充電上限を 50% にする — 純正の仕組みをそのまま使う

## TL;DR

- Galaxy A23 5G (SCG18、au 版、Android 14 / One UI 6.1) の純正「バッテリーを保護」は、最大でも 80% までしか上限を下げられない
- しかし内部の閾値はただの整数で、カーネル側にホワイトリストは無い。設定を書けば 50% でも止まることを実機で実証した
- 上限で止まっている間は電池が分離され、アダプタが直接給電する（いわゆるフロート充電ではない）。常時給電の端末を低電圧で寝かせる用途にちょうどいい
- 実装は「設定を書く小さなアプリ」＋「起動後に遅れて書き直すスクリプト」。常駐デーモンは無し
- 途中で services.jar の書き換えと純正画面の改変にも挑戦した。前者は正しい手順なら通る、後者は署名の壁で不可能、という結論になった

前提: root 化済み (Magisk) の自分の端末での作業です。再現する場合は自己責任で。機種・ビルドが違えば挙動も変わります。

## なぜ 50% か

対象の端末は、挿しっぱなしで常時給電される作業用端末です。この使い方で電池を一番傷めるのは「高電圧のまま放置される時間」です。残量 80% のときの電圧は約 4.13V、50% では約 3.85V。この差が放置劣化の差になります。

純正の保護機能は「標準 (100%)」と「最大 (80%)」の2択しかありません。50% で寝かせたいなら、自分で何とかするしかない、というのが出発点です。

## 純正の仕組みを調べた

### 執行しているのは BatteryService

充電上限の実体は、Android の BatteryService (Samsung 拡張版) が sysfs のノードへ値を書く仕組みでした。

- 設定は Settings.Global の2キー: モード `protect_battery` と閾値 `battery_protection_threshold`
- カーネル側の受け口は `/sys/class/power_supply/battery/batt_full_capacity` で、「値＋接尾辞 (OPTION 等)」の形式
- 停止と再開の規則は単純で、**残量が設定値に達したら停止、設定値−2% まで落ちたら再開、100 で機能オフ**
- Java 側にもカーネル側にも、値のホワイトリストや範囲の制限らしい制限は無い (範囲外は黙って無視される)。つまり 80 という数字は「UI が出している上限」であって、機構の上限ではない

### 閾値が効くまでの癖

ここが一番の罠でした。閾値は起動時に1回だけ読まれ、変更を監視する仕組みがありません。

- 起動時の処理順序は「モードを読む → その場で値を書きに行く (この時点の閾値は初期値の 80) → その後に設定から閾値を読み込む」
- したがって、閾値だけ書き換えて再起動しても、起動直後は 80 (またはオフなら 100) が書かれる
- 書いた閾値が実際に sysfs へ出るのは、「読み込みが終わった後のセッションで、モード変更イベントが発火したとき」だけ

この挙動は、逆コンパイルしたコードの精読と、実機での再起動テストの両方で一致しました。実務的な手順は「閾値を書く → 再起動 → モードを一度 0 にして 1 に戻す (これで書き込みが発火する) → sysfs と /efs の読み戻しで確認」になります。

### 止まっている間、電池は休んでいる

上限で停止している状態で CPU 負荷をかけても、電池電流はほぼ 0mA で、電圧も垂れませんでした。この機種の充電 IC (MediaTek 系) には電源パスがあり、充電を止めると電池が回路から分離され、システムはアダプタから直接給電されます。

つまり上限保持は「満充電付近で微充電を続ける」状態ではなく、「電池を切り離して休ませる」状態です。78% への再開線が効くのは、電池が実際に減った場合だけになります。

### 実証 (最小構成)

アプリを作る前に、手作業で一巡を実証しました。

- 閾値 55 でテスト: 放電して 53% (=55−2) で充電が再開し、55% ちょうどで停止。規則どおり
- 閾値 50 でも同様に、カーネルが "50 OPTION" を受理し、上限超過のまま停止を維持することを確認

## 作ったもの: 小さな置き換えアプリ

設定画面の代わりに、上限を選ぶだけのアプリを作りました (以下 protectcap と呼びます)。

- 選択肢は オフ (100%) / 80% / 60% / 50% の4つ。70 や 90 は使う状況が無く、40 は 50 との劣化差が誤差級なので外しました
- 選ぶと root で: 設定DBへ閾値を書く → モードを 0→1 と切り替えて BatteryService に書かせる → 最後に sysfs と /efs へ直接書いて揃える → 自分の選択値をファイルに保存する
- 常駐はしません。開いている間だけ存在する普通のアプリです (メモリは実測で約 29MB、閉じれば 0)
- root 許可のトーストが毎回出るのが煩わしいので、Magisk のポリシーでこのアプリの通知はオフにしています

## 脱線1: services.jar の起動順序を直す

「起動直後に 80 が書かれる癖」は、BatteryService 本体の処理順序が原因です。ならば jar の中の命令順序を入れ替えて、閾値を読んでから書くようにすれば根絶できます。

### v1 の失敗: VerifyError

dex のバイト列を直接いじる方法で挑戦した初版は、起動時に落ちました。`/data/log/rescueparty_log` を読むと原因は明快で、移動した命令ブロックに含まれていたレジスタ番号が、移動先メソッドのレジスタ枠 (10 本) を超えていて、ART の検証器に弾かれていたのです。system_server が繰り返し落ち、警告ダイアログとセーフモードの発動まで行きました。

教訓: 「監視に捕まった」のではなく「書き換えの作りが悪くて自滅した」。ログはそう言っていました。

### v2 の成功: smali で再構築する

smali/baksmali で一度テキストに戻し、対象メソッド内の「閾値の読み込み」を「書き込みの呼び出し」より前へ移して、再構築し直しました。レジスタの再割り当てが正しく行われるため検証を通り、再起動しても警告なしで起動し、起動直後から 80 を経由せず 50 が書かれるようになりました。

なお、改変した jar そのものは配布しません (Samsung のソフトウェアの改変物になるため)。ここに書いた「方法」だけが共有できる部分です。

## 脱線2: 純正画面に選択肢を増やす

純正の保護画面 (デバイスケア配下のアプリ、本記事では lool と呼びます) を調べると、面白いものが見つかりました。画面のレイアウトには、最大の下に4段のスライダーが既に入っているのです (非表示)。目盛りは 80/85/90/95 で、変換式と、離したときに設定へ書く経路まで全部配線済みでした。変換式を 80/70/60/50 に書き換えれば、そのまま使えそうです。

しかし APK の差し替えはできませんでした。理由は署名です。

- lool はシステム権限を共有する特権アプリで、プラットフォーム鍵 (端末のフレームワークと同じ鍵) で署名されている
- 自前の鍵で署名した APK に差し替えると、PackageManager が署名不一致で弾き、system_server が落ち続けてリカバリ画面送りになった (実際にやらかしました)
- プラットフォーム鍵の秘密鍵はメーカー社内物で、入手手段が無い

services.jar の差し替えが通ったのは、フレームワークの jar が APK のような署名検証の対象外だからで、アプリとは扱いが違います。「特権アプリの差し替えは、プラットフォーム鍵なしでは不可能」が結論です。プロセス内フック (Xposed 系) なら署名と無関係に届く余地はありますが、今回は採用しませんでした。

なお、純正画面の説明文に出る「80%」は、設定ではなくコードに埋め込まれた固定値でした。実効が 50 でも表示は 80 のまま、という状態が残っています (見た目だけの問題)。

## 最終方式: 遅れて書き換える

画面の改変ができない以上、起動直後にオリジナルが 100 や 80 を書くこと自体は止められません。そこで発想を逆にしました。**オリジナルが先に書くなら、後から書き直せばいい**。

- Magisk の service.d に置いたシェルスクリプトが、起動後 約1分 / 約3分 / 約5分 の3回、保存しておいた選択値を同じ手順で書き直す
- 3段にしているのは保険です。事故のときの観測で「起動後に設定が 0 に戻される後出しの変化」が起きたことがあり、1回だけの書き直しではそれに負けるためです
- スクリプトは3回書いたら終了します。常駐プロセスは残らず、メモリも残りません
- service.d のスクリプトは Magisk デーモンの権限で走るので、root 許可のダイアログやトーストは一切出ません

注意点として、セーフモードやリカバリ経由の起動では service.d 自体が走りません。その場合は上限が 100 に戻ったままになるので、通常起動での復旧が必要です。

スクリプトの全文は付録に置きます。

## 実測まとめ

- 復旧ブートの実測: 起動 22 秒でオリジナルが 100 を書く → 59 秒で1段目が 50 に書き直し、設定・sysfs・/efs が全部 50 で一致。2・3段目は同じ値の再書きで、起動後 7 分時点でも 50 を維持
- 実地確認: 残量 50% の状態で充電器を挿しても、充電は始まらず Not charging・電流ほぼ 0mA を維持 (AC の接続自体は認識されている)
- 再開側: 48% まで落ちれば純正の規則で充電が再開し、50% で再び止まる

## 残っていること

- 純正画面の表示は 80% のまま (実効は正しい)。直すならフック方式の検討が要る
- 後出しの設定変化が 5 分より後に来るケースは観測できていない。3段で足りないようなら、その時点で常駐型を検討する
- この記事は SCG18 の特定ビルドでの実測です。他機種では受け口のノード名から違う可能性があります

## 付録: 起動時スクリプト (全文)

```sh
#!/system/bin/sh
# バッテリー保護 起動時ワンショット — 遅れて書き直す方式
# 置き場所: /data/adb/service.d/protectcap_boot.sh (Magisk が起動時に1回だけ実行)
#
# オリジナル (BatteryService) は起動時に 100 か 80 を書く。それを止めることは
# できないので、後から3段 (約60秒 / 約180秒 / 約300秒) で選択値を書き直す。
# 毎回ログに「書く前の状態 / 書いた後の読み戻し」を残す。常駐はしない。
# value ファイル: /data/adb/protectcap/value … 0=オフ / 50,60,80=上限

VFILE=/data/adb/protectcap/value
LOG=/data/adb/protectcap/boot_apply.log
[ -f "$VFILE" ] || exit 0
V=$(cat "$VFILE" 2>/dev/null)
case "$V" in
  0|50|60|80) ;;
  *) exit 0 ;;
esac

# sysfs が生えるまで少し待つ
i=0
while [ $i -lt 30 ]; do
  [ -e /sys/class/power_supply/battery/batt_full_capacity ] && break
  sleep 2
  i=$((i+1))
done

apply_once() {
  # $1 = 段のラベル。書く前に状態を記録し、書いた後に読み戻して記録する
  PB_BEFORE=$(settings get global protect_battery 2>/dev/null)
  FC_BEFORE=$(cat /sys/class/power_supply/battery/batt_full_capacity 2>/dev/null)
  if [ "$V" = "0" ]; then
    settings put global battery_protection_threshold 80
    settings put global protect_battery 0
  else
    settings put global battery_protection_threshold "$V"
    settings put global protect_battery 0
    sleep 1
    settings put global protect_battery 1
    sleep 1
    echo "$V OPTION" > /sys/class/power_supply/battery/batt_full_capacity
    echo "$V" > /efs/Battery/batt_full_capacity
    echo 0 > /sys/class/power_supply/battery/batt_soc_rechg
  fi
  sleep 2
  PB_AFTER=$(settings get global protect_battery 2>/dev/null)
  FC_AFTER=$(cat /sys/class/power_supply/battery/batt_full_capacity 2>/dev/null)
  UP=$(cut -d' ' -f1 /proc/uptime)
  echo "stage=$1 up=${UP}s V=$V pb:${PB_BEFORE}->${PB_AFTER} fullcap:${FC_BEFORE}->${FC_AFTER} $(date +%H:%M:%S)" >> "$LOG"
}

# 1段目: 起動から約60秒
sleep 45
apply_once 1
# 2段目: 約180秒
sleep 120
apply_once 2
# 3段目: 約300秒
sleep 120
apply_once 3
exit 0
```
